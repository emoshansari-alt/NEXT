## D-001 — Development happens on Windows; verification is tiered

**Date:** 2026-08-08 · **Status:** Accepted

**Context.** The development machine is Windows 11 Home (10.0.26200). Xcode is macOS-only.
There is no supported way to compile SwiftUI, UIKit, SwiftData, WidgetKit, StoreKit or iOS
XCTest, or to run the iOS Simulator, on Windows. This is a platform fact, not a preference, and
it is a *separate and earlier* constraint than the absent Apple Developer Program membership:
membership blocks distribution, the missing Mac blocks compilation of the app layer.

**Decision.** Keep the settled stack (Swift, SwiftUI, Xcode, iPhone-first) unchanged. Split
verification into three tiers and require every status claim in this repository to name its tier.

| Tier | Environment | Proves | Membership needed |
|---|---|---|---|
| 1 | Windows + Swift toolchain | `NextKit` compiles; core logic tests genuinely pass | no |
| 2 | GitHub Actions `macos-latest` | App compiles; Simulator unit/UI tests; a11y audit; local StoreKit | no |
| 3 | Physical device + paid membership | Device behaviour, TestFlight, submission | yes |

**Reasoning.** Tier 2 is the key unlock. GitHub-hosted macOS runners can run `xcodebuild` and
iOS Simulator tests against an unsigned build; code signing is only required for physical
devices and distribution. That means the SwiftUI layer can be genuinely compiled and
Simulator-tested from a Windows machine with no Mac hardware and no paid membership.

**Rejected alternatives.** Changing to React Native / Flutter / a web app — out of scope, the
stack is settled, and it would not be a technical necessity, only a convenience. Hand-writing
Swift blind with no compiler anywhere — produces unverifiable claims, which the project
explicitly forbids.

**Open.** Whether the owner has any Mac access is unknown; it would accelerate Tier 2 but is
not required. Tracked as an escalation in `SESSION_LOG.md`.

## D-002 — `NextKit` / `NextApp` module split

**Date:** 2026-08-08 · **Status:** Accepted

**Decision.** All product decision logic lives in `NextKit`, a Swift package depending only on
Foundation. `NextApp` is a thin SwiftUI shell over it.

**Reasoning.** Three payoffs. (a) The ranking engine becomes a pure function over value types
and is trivially unit-testable, which §26 of the product spec demands. (b) Because it has no
Apple-UI dependency it compiles and its tests *run* on Windows — this is what makes Tier 1 real
work rather than blind authoring. (c) Persistence and intelligence sit behind protocols, so
SwiftData or any model vendor can be replaced without touching product logic.

This split would be the right architecture even on a Mac. The platform constraint made it
urgent, not arbitrary.

**Enforcement.** CI fails if `NextKit` sources contain `import SwiftUI`, `import UIKit`,
`import SwiftData`, `import WidgetKit`, `import StoreKit`, or `import UserNotifications`.

## D-003 — The Xcode project is generated by XcodeGen, not committed

**Date:** 2026-08-08 · **Status:** Accepted

**Decision.** Commit a declarative `project.yml`. Generate `NextApp.xcodeproj` with
`xcodegen generate`. Gitignore the generated project.

**Reasoning.** A `project.pbxproj` cannot be reliably hand-authored or reviewed from Windows,
is notoriously merge-hostile, and drifts silently from intent. A YAML spec is diffable,
reviewable, and reproducible in one command on any Mac or CI runner. XcodeGen is a build-time
tool only — it ships nothing into the app, so it does not count against the dependency policy.

**Rejected.** Tuist (heavier, more concept surface than this project needs). Hand-forging
pbxproj (fragile, unreviewable from this machine).

## D-004 — Deployment target: iOS 17.0

**Date:** 2026-08-08 · **Status:** Accepted, revisit at Phase 8 · **Verify before release**

**Decision.** Minimum deployment target iOS 17.0. Build against the current SDK.

**Reasoning.** iOS 17 is the floor that provides SwiftData and the Observation framework
(`@Observable`), both of which the intended architecture uses directly. The audience is
students aged 16–22, a group disproportionately likely to be carrying older or hand-me-down
hardware, so a generous floor matters more here than for a typical productivity app. By
mid-2026 an iOS 17 floor still reaches effectively the entire supported-device population.

**Consequence — this is the important one.** Apple's on-device Foundation Models framework
requires a far newer OS *and* Apple Intelligence–capable hardware, which is a small minority of
this audience's devices. Therefore on-device generative AI **cannot** be the only intelligence
path, and the provider abstraction plus deterministic fallback in D-005 are structurally
required rather than merely prudent. This is a direct architectural consequence of who the
users are.

**Risk.** Early SwiftData releases had known rough edges. Mitigated by D-006: all persistence
is reached through `TaskRepository`, so a fallback to Core Data is a one-module change.

**To verify at Phase 8** (with current documentation, not from memory): exact current OS/hardware
requirements for Foundation Models, and current iOS version-share data.

## D-005 — Intelligence is behind a provider protocol with a mandatory validator

**Date:** 2026-08-08 · **Status:** Accepted (provider choice deferred to Phase 8)

**Decision.** Define `IntelligenceProvider` in `NextKit`. Every provider response passes through
a non-bypassable `ResponseValidator` before any state mutation. Ship a
`TemplateFallbackProvider` that performs deterministic extraction and template-based rescue
with no model and no network.

**Reasoning.** Product invariants P3 (AI is advisory), P6 (AI earns its usage) and P7 (offline
works) all require this shape. It also keeps the Phase 8 vendor question genuinely open instead
of being decided by accident of whatever gets written first.

**Deferred to Phase 8:** which concrete provider(s) ship in 1.0, whether any cloud provider is
needed at all for 1.0, and the associated key-handling architecture (see D-009).

## D-006 — Persistence behind `TaskRepository`; SwiftData as the initial implementation

**Date:** 2026-08-08 · **Status:** Accepted

**Decision.** `NextKit` defines a `TaskRepository` protocol over value types and ships an
in-memory implementation for tests. `NextApp` provides the SwiftData-backed implementation and
maps `@Model` classes to/from `NextKit` value types at that boundary.

**Reasoning.** Keeps the domain free of the persistence framework, makes the whole domain layer
testable at Tier 1, and makes D-004's SwiftData risk cheap to reverse.

**Cost, stated honestly.** Mapping between `@Model` classes and value types is real boilerplate.
Accepted deliberately in exchange for testability and reversibility.

## D-007 — No `Date()` or `UUID()` inside `NextKit`

**Date:** 2026-08-08 · **Status:** Accepted

**Decision.** Time and identity are injected via `Clock` and `IDProvider`. A CI lint fails the
build on a direct `Date()` or `UUID()` call in `NextKit` sources.

**Reasoning.** Ranking is deadline-driven; a hidden clock read makes tests time-dependent and
flaky, and makes deadline edge cases (overdue, due-in-one-hour, impossible) impossible to test
honestly. Injection is the difference between a testable engine and one that merely has tests.

## D-008 — Ranking weights live in exactly one place

**Date:** 2026-08-08 · **Status:** Accepted

**Decision.** One `ScoringWeights` value type holds every scoring constant, with documented
defaults and rationale per field. No scoring constant may appear elsewhere.

**Reasoning.** Required by product spec §5. It also makes tuning a data change rather than a
code change, and makes "Why this?" generatable, since each factor's contribution is nameable.

## D-009 — No production secret ships in the client

**Date:** 2026-08-08 · **Status:** Accepted (architecture deferred with D-005)

**Decision.** No production API key is embedded in the app binary or committed. If Phase 8
concludes that a cloud model is genuinely required for 1.0, a minimal token-broker backend is
designed then and justified in a new decision entry. A backend is permitted when security
requires it — never merely because apps usually have one.

**Reasoning.** A key shipped in an iOS binary is extractable and must be treated as public.

## D-011 — Analytics deferred; crash visibility prioritised

**Date:** 2026-08-08 · **Status:** Provisional, decide at Phase 14

**Decision.** No analytics SDK is integrated now. Aggregate event *names* are defined in the
product spec so instrumentation points can be designed, but nothing is wired to a vendor.

**Reasoning.** The product spec explicitly permits shipping with no third-party analytics and
notes crash visibility is likely more valuable. Adding an SDK now would create a privacy and
dependency cost before there is any evidence it is needed.

## D-013 — The time seam is `TimeSource`, not `Clock` (supersedes the naming in D-007)

**Date:** 2026-08-08 · **Status:** Accepted

**Context.** D-007 named the injected seams `Clock` and `IDProvider`. `Clock` collides with the
Swift standard library's own `Clock` protocol — the one behind `ContinuousClock` and
`Task.sleep(until:)`.

**Evidence, observed rather than predicted.** While the seam was still called `Clock`, its own
test file could not conform to it without writing `NextKit.Clock`, and had to spell the
existential `any NextKit.Clock`. Which uses resolve silently and which the compiler rejects
depends on what else is in scope. That uncertainty lands hardest in `NextApp`, which cannot be
compiled from the Windows development machine — so the cost would have been paid a CI cycle
at a time, after every call site was already written against the bad name.

**Decision.** Rename the protocol to `TimeSource`, with `SystemTimeSource` in `NextApp` and
`FixedTimeSource` in tests. `IDProvider` is unchanged — it collides with nothing.

**What D-007 still says.** Everything else in D-007 stands unaltered: `NextKit` may not call
`Date()` or `UUID()`, both are injected, and `scripts/lint-nextkit.sh` enforces it. Only the
name of the time protocol changes. D-007's text is left as written because this file is
append-only; this entry is the correction.
